### Common patterns & fixes

What came up across many submissions (we'll livecode fixes for the most common):

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Scene changes skip ahead or flicker | scene change inside `draw()` on `mouseIsPressed` / `keyIsPressed` | move it into `mousePressed()` / `keyPressed()` (runs once per press) |
| Objects vanish or get skipped when removed | `splice()` in a forward loop | loop **backwards** |
| Image never shows (p5 2.x) | `preload()` or missing `await` | `async function setup()` + `await loadImage()` |
| DOM button only works with a mouse | `.mousePressed()` | `.mouseClicked()` |
| Arrow keys move a slider *and* the character | the slider still has keyboard focus | click the canvas, or call `.elt.blur()` after it changes |
| Controls pile up across scenes | `create___()` called in `draw()` or on every scene change | create once in `setup()`; `.show()` / `.hide()` per scene |
| Screen reader says nothing | no `describe()`, or the same one for every scene | `describe()` inside each `case` |

## Lecture #11 Discussion: Artificial Sensing

### Notes

Last week we asked what a screen reader "sees" when it looks at your canvas. This week flips it: what does a *machine* sense when it looks at *us*?

- A sensor turns something in the world (light, sound, motion, heat) into **numbers**. Everything after that is a choice someone made about what those numbers mean.
- "Artificial sensing" is never neutral: someone decides **what gets measured**, **what counts as a category**, and **who it was tested on**.
- Your web page is sensed too: search engines, screen readers, and AI scrapers all read your HTML, not your pixels. The structure you choose today is what they understand.

### Discuss

Quick pair discussion (5 min), pick one:

1. Name a sensor you were "read" by today (phone unlock, door, transit card, camera). What did it measure? What did it *decide* from that measurement?
2. Who is missing from the data a sensing system was trained on, and what happens to them when it's deployed?
3. Last week: alt text written by a person vs. alt text generated by an AI. What does each one notice? What does each one miss?
4. Your portfolio will be read by people, screen readers, search engines, and AI crawlers. What do you want each of them to understand about your work?

### HTML Introduction

Last week we peeked at the HTML file around our p5 sketch. This week we write a page ourselves.

**HTML (HyperText Markup Language)** describes the **structure** and **meaning** of content on a web page. It is not a programming language: there are no variables, loops, or `if` statements. It *labels* content: "this is a heading," "this is a link," "this is a list."

The three languages of the web each do one job:

| Language | Job | In a house |
| --- | --- | --- |
| **HTML** | structure & meaning | the walls and rooms |
| **CSS** | appearance | the paint and furniture |
| **JavaScript** | behavior | the electricity and plumbing |

To make an HTML file, create a file ending in `.html` (the homepage of a site is almost always `index.html`) and open it in a browser.

> **See it:** on any web page, right-click → **View Page Source** to see its HTML, or **Inspect** to see the live DOM.

### HTML Elements

An **element** is made of an opening tag, content, and a closing tag:

```html
<p>This is a paragraph.</p>
<!-- ^ opening tag   ^ closing tag (note the /) -->
```

#### Nesting

Elements go inside other elements, like boxes in boxes. **Close them in the reverse order you opened them.**

```html
<!-- correct -->
<p>This is <strong>very</strong> important.</p>

<!-- wrong: tags overlap -->
<p>This is <strong>very</p></strong>
```

#### Empty (void) elements

Some elements have no content and no closing tag:

```html
<img src="sketch.png" alt="A green seed on sand">
<br>
<hr>
```

#### Common elements

| Element | What it is |
| --- | --- |
| `<h1>` … `<h6>` | headings, from most to least important |
| `<p>` | paragraph |
| `<a>` | link |
| `<img>` | image |
| `<ul>` / `<ol>` / `<li>` | unordered list / ordered list / list item |
| `<strong>` / `<em>` | strong importance / emphasis |
| `<figure>` / `<figcaption>` | an image or embed with a caption |
| `<iframe>` | a web page inside your web page (like an embedded sketch) |
| `<div>` / `<span>` | generic boxes with **no meaning** (block / inline) |

**Block** elements (`<p>`, `<h1>`, `<div>`, `<ul>`) start on a new line and take the full width. **Inline** elements (`<a>`, `<strong>`, `<span>`, `<img>`) sit inside a line of text.

### Document Structure

Every HTML page has the same skeleton:

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Morgan's Portfolio</title>
  </head>
  <body>
    <h1>Hello, world.</h1>
    <p>This is my page.</p>
  </body>
</html>
```

| Line | What it does |
| --- | --- |
| `<!DOCTYPE html>` | tells the browser "this is modern HTML" |
| `<html lang="en">` | the root element; `lang` tells screen readers which language to pronounce |
| `<head>` | information **about** the page: not shown on the page |
| `<meta charset="UTF-8">` | lets the page show any character: é, ñ, 漢字, 🐸 |
| `<meta name="viewport" ...>` | makes the page fit phone screens |
| `<title>` | the text in the browser tab, bookmarks, and search results |
| `<body>` | everything visible on the page |

Indent nested elements. The browser doesn't care, but you (and anyone reading your code) will.

> **Shortcut:** in VS Code, type `!` and press **Tab** in an empty `.html` file to get this skeleton.

### Attributes

Attributes give an element extra information. They go in the **opening tag** as `name="value"`:

```html
<a href="https://openprocessing.org" target="_blank">OpenProcessing</a>
<!-- ^ element  ^ attribute name="value" -->
```

| Attribute | On | What it does |
| --- | --- | --- |
| `href` | `<a>` | where the link goes |
| `src` | `<img>`, `<iframe>`, `<script>` | the file or page to load |
| `alt` | `<img>` | text alternative: read by screen readers, shown if the image breaks |
| `title` | `<iframe>` | names an embed for screen readers |
| `width` / `height` | `<img>`, `<iframe>` | size in pixels |
| `id` | any | a **unique** name for one element (also a link target: `href="#about"`) |
| `class` | any | a name you can reuse on many elements (we'll style these with CSS) |
| `lang` | `<html>`, any | the language of the content |

#### Paths

`href` and `src` can be **absolute** (a full URL) or **relative** (from where this file is):

```html
<img src="https://example.com/frog.png" alt="...">  <!-- absolute -->
<img src="images/frog.png" alt="...">               <!-- relative: a folder next to index.html -->
<a href="about.html">About</a>                       <!-- relative: another page -->
<a href="#projects">Projects</a>                     <!-- same page: the element with id="projects" -->
```

File names: lowercase, no spaces (`origin-story.png`, not `Origin Story FINAL(2).PNG`). Paths are case-sensitive on most servers.

#### Writing good `alt` text

- Describe what matters **in context**, not every pixel: "Screenshot of my Frogger game: a frog dodging five lanes of traffic."
- Don't start with "image of": the screen reader already says "image."
- Decorative image? Use `alt=""` (empty, not missing) so the screen reader skips it.
- Remember *Alt Text as Poetry*: description can be creative.

### Best Practices & Semantic HTML

**Semantic** HTML means choosing elements for what content **is**, not what it looks like. A `<div>` says nothing; a `<nav>` says "this is navigation." Screen readers, search engines, and AI crawlers all use this to understand (and navigate) your page. Same lesson as last week's `createButton()` vs. `rect()`: **the right element gives you access for free.**

#### Page landmarks

```html
<body>
  <header>
    <h1>Your Name</h1>
    <nav>
      <a href="#projects">Projects</a>
      <a href="#about">About</a>
    </nav>
  </header>

  <main>
    <section id="projects">
      <h2>Projects</h2>
      <article>
        <h3>Origin Stories</h3>
        <p>...</p>
      </article>
    </section>

    <section id="about">
      <h2>About</h2>
      <p>...</p>
    </section>
  </main>

  <footer>
    <p>© 2026 Your Name</p>
  </footer>
</body>
```

| Element | Meaning |
| --- | --- |
| `<header>` | intro content: your name, logo, nav |
| `<nav>` | the main links around the site |
| `<main>` | the main content (**one per page**) |
| `<section>` | a themed group of content, usually with a heading |
| `<article>` | something that stands on its own: one project, one post |
| `<aside>` | related, but secondary |
| `<footer>` | closing info: contact, credits, copyright |

Screen reader users can jump straight between landmarks and headings. A page made of `<div>`s is one long, unmarked hallway.

#### Best practices checklist

1. **One `<h1>` per page**, and don't skip heading levels (`h1` → `h2` → `h3`, not `h1` → `h4`). Pick headings for *outline*, not *size*; CSS handles size.
2. **Links say where they go.** "See Origin Stories" instead of "click here."
3. **Every `<img>` has `alt`.** Every `<iframe>` has a `title`.
4. **Use `<button>` for actions and `<a>` for going places.**
5. **Lists are lists.** Three projects in a row? `<ul>` + `<li>`.
6. **`<div>` and `<span>` are a last resort**, for when no semantic element fits (usually for styling).
7. **Lowercase tags, quoted attributes, consistent indentation.**
8. **Validate** with the [W3C Validator](https://validator.w3.org/#validate_by_input): paste your HTML and fix every error.

## Pair Exercise: Div Soup

Someone built their portfolio with only `<div>`s and `<span>`s. It *looks* fine in a browser, but to a screen reader, a search engine, or an AI crawler, it's soup. Make it semantic.

Work in pairs. Create `index.html` with the code below and open it in a browser.

### The starter

```html
<html>
<head>
<title>portfolio</title>
</head>
<body>
<div class="top">
  <div class="big">JAMIE CHEN</div>
  <div class="links">
    <span onclick="location.href='#work'">work</span>
    <span onclick="location.href='#info'">info</span>
  </div>
</div>

<div id="work">
  <div class="big">My Work</div>
  <div class="project">
    <div class="medium">Bubble Garden</div>
    <div>A sketch where bubbles float around. <b>click here</b> to see it:
      <a href="https://openprocessing.org/sketch/0000004">here</a></div>
    <img src="Bubble Garden FINAL.PNG">
  </div>
  <div class="project">
    <div class="medium">Picking Fruit</div>
    <div>Me and my partner made this in class.
    <img src="images/fruit.png">
  </div>
</div>

<div id="info">
  <div class="big">About Me</div>
  <div>I like <i>frogs</i>, <i>noodles</i>, and <i>code</i>.</div>
</div>

<div class="bottom">jamie 2026</div>
</body>
</html>
```

### Steps

1. **Skeleton.** Add `<!DOCTYPE html>`, `lang="en"`, `<meta charset="UTF-8">`, the viewport `<meta>`, and a real `<title>`.
2. **Landmarks.** Replace the outer `<div>`s with `<header>`, `<nav>`, `<main>`, `<section>`, and `<footer>`. Each project should be an `<article>`.
3. **Headings.** Replace every `class="big"` / `class="medium"` with the right heading level. Only one `<h1>`! (Hint: does "My Work" deserve the same level as the person's name?)
4. **Links.** The nav `<span>`s only work with a mouse. Make them real `<a>` links. Rewrite "click here … here" so the link says where it goes.
5. **Images.** Give every `<img>` an `alt`. Rename `Bubble Garden FINAL.PNG` to a web-safe path.
6. **Find the bug.** One element is never closed. Find it (the validator will help).
7. **Meaning.** `<b>` and `<i>` describe *looks*. Should "frogs, noodles, and code" be emphasized, or should it be a list? Decide together.

*Stretch (pick one):*

- **Figures.** Wrap each image in `<figure>` with a `<figcaption>`.
- **Embed.** Replace one image with an OpenProcessing `<iframe>` (with a `title`).
- **Second page.** Make `about.html`, move the About section there, and link between the two pages.
- **Hear it.** Listen to the *original* div-soup page and your fixed page with a screen reader. What did the soup version announce?

*Share-out:* one pair projects their page and navigates it **headings-only** with the screen reader rotor.

## Coding Glossary

| Term | Meaning |
| --- | --- |
| HTML | HyperText Markup Language: labels the structure and meaning of a web page |
| element | one piece of the page: opening tag + content + closing tag |
| tag | the `<name>` and `</name>` markers around content |
| void element | an element with no content or closing tag: `<img>`, `<br>`, `<meta>` |
| nesting | putting elements inside other elements; close them in reverse order |
| attribute | extra info in an opening tag: `name="value"` |
| `<!DOCTYPE html>` | first line of every page: "this is modern HTML" |
| `<head>` | information about the page (title, meta, scripts); not shown |
| `<body>` | everything visible on the page |
| `<meta>` | data about the page: character set, viewport, description |
| block / inline | starts a new line and fills the width / sits inside a line of text |
| absolute path | a full URL: `https://example.com/frog.png` |
| relative path | a path from the current file: `images/frog.png` |
| `id` | a unique name for one element; also a same-page link target |
| `class` | a reusable name for a group of elements (for CSS) |
| semantic HTML | choosing elements for what content *is*, not how it looks |
| landmark | a page region screen readers can jump to: `header`, `nav`, `main`, `footer` |
| `<div>` / `<span>` | generic containers with no meaning |
| heading outline | the tree your `h1`–`h6` make; how screen readers skim a page |
